# Deploying to Render

## How many env vars do you need?

**Locally:** 12 variables in `backend/.env` (a 13th, `DATABASE_URL`, is
optional — leave it blank and Django falls back to SQLite automatically).

**On Render:** the same 12, but `render.yaml` auto-fills 5 of them for you
(`SECRET_KEY`, `JWT_SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, `DATABASE_URL`).
You manually fill in **7**: `FRONTEND_URL`, 3 Cloudinary keys, plus
`JWT_EXPIRES_DAYS` / `COOKIE_EXPIRE_DAYS` / `COOKIE_SAMESITE` /
`COOKIE_SECURE` are also pre-filled with sane production defaults — so
realistically you only *type in* **4 values**: `FRONTEND_URL` and your 3
Cloudinary credentials. The frontend needs **1 more**: `VITE_API_URL`.

## Full variable reference

| Variable | Where | Local value | Render value |
|---|---|---|---|
| `SECRET_KEY` | backend | any random string | auto-generated by Render |
| `DEBUG` | backend | `True` | `False` (set by render.yaml) |
| `ALLOWED_HOSTS` | backend | `*` | `.onrender.com` (set by render.yaml) |
| `FRONTEND_URL` | backend | `http://localhost:5173` | **your frontend's live URL** (you fill in) |
| `JWT_SECRET_KEY` | backend | any random string | auto-generated by Render |
| `JWT_EXPIRES_DAYS` | backend | `5` | `5` (set by render.yaml) |
| `COOKIE_EXPIRE_DAYS` | backend | `5` | `5` (set by render.yaml) |
| `COOKIE_SAMESITE` | backend | `Lax` | `None` (set by render.yaml — required for cross-domain cookies) |
| `COOKIE_SECURE` | backend | `False` | `True` (set by render.yaml — cookie only sent over HTTPS) |
| `CLOUDINARY_CLIENT_NAME` | backend | your Cloudinary cloud name | same (you fill in) |
| `CLOUDINARY_CLIENT_API` | backend | your Cloudinary API key | same (you fill in) |
| `CLOUDINARY_CLIENT_SECRET` | backend | your Cloudinary API secret | same (you fill in) |
| `DATABASE_URL` | backend | blank (uses SQLite) | auto-filled from the Postgres database (set by render.yaml) |
| `VITE_API_URL` | frontend | not set (falls back to `http://localhost:4000`) | **your backend's live URL** (you fill in) |

## Why `FRONTEND_URL` and `VITE_API_URL` can't be pre-filled

They each need the *other* service's live URL, but neither URL exists until
that service has been deployed once. This is a real chicken-and-egg problem,
not a mistake in the config — every two-service Render deploy hits it.
`render.yaml` marks both as `sync: false` so Render prompts you for a value
instead of guessing.

## Step-by-step

### 1. Push this project to a GitHub repo
Render deploys from a connected Git repo. Commit `backend/`, `frontend/`,
and `render.yaml` (at the repo root) and push.

### 2. Create the Blueprint
In the Render dashboard: **New → Blueprint** → connect your repo → Render
reads `render.yaml` and shows you `jobg-backend`, `jobg-frontend`, and
`jobg-db`. Click **Apply**.

### 3. First deploy will look "broken" — that's expected
Render will ask you to fill in the `sync: false` variables
(`FRONTEND_URL`, the 3 Cloudinary keys, `VITE_API_URL`) before it can
deploy. For the first pass:
- Cloudinary keys: fill in now (you already have these).
- `FRONTEND_URL` and `VITE_API_URL`: put in *anything* for now (e.g.
  `http://localhost`) just to get both services to deploy once.

### 4. Copy the real URLs
Once both services show **Live**, copy their URLs from the Render
dashboard — they'll look like:
- Backend: `https://jobg-backend.onrender.com`
- Frontend: `https://jobg-frontend.onrender.com`

### 5. Fix the two variables for real
- On `jobg-backend` → Environment → set `FRONTEND_URL` to your actual
  frontend URL (`https://jobg-frontend.onrender.com`).
- On `jobg-frontend` → Environment → set `VITE_API_URL` to your actual
  backend URL (`https://jobg-backend.onrender.com`).

Saving either variable triggers a redeploy of that service automatically.

### 6. Test it
Open the frontend URL, register a user, and confirm you stay logged in
after a refresh — that confirms the cross-domain cookie (`SameSite=None;
Secure`) is working correctly.

## Notes
- Both services are on Render's **free plan** in this config — free web
  services spin down after inactivity and take ~30–60s to wake up on the
  next request. Fine for demos/practice, not for production traffic.
- The free Postgres database expires after 30 days on Render's free tier;
  you'll need to recreate it (or upgrade) after that.
- If you ever see login work but `getuser` fail right after (session
  doesn't persist), it's almost always `FRONTEND_URL` or `VITE_API_URL`
  still pointing at the placeholder value from step 3 — double check both.
